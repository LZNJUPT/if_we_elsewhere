# IMPORT · 数据导入指南（数据规范 v2）

## 合规边界（先读这个）

- 本项目**不解析微信数据库、不提供任何抓取功能**，也不教程化「怎么导出」。
- 你只能导入**你自己合法导出**的聊天记录文件，并对其合法性负责。
- 导入即脱敏：手机号/身份证/银行卡/车牌/邮箱/地址等模式会被替换为
  `[手机号]`、`[地址]` 之类的占位符，脱敏文本（`content_clean`）才是后续
  分析与 LLM 的唯一输入。
- **媒体（表情包 / 图片）是例外：不做脱敏**。见下文「媒体导入」一节的红线说明。

## 数据从哪来（v0.3）

IfWe **只消费你自己合法导出的聊天记录文件**，不解析任何聊天软件的数据库。

| 格式标识 | 来源工具 | 导出物 | 说明 |
|---|---|---|---|
| `chatlab` | [WeFlow](https://github.com/hicccc77/WeFlow) | JSONL | IfWe 的原生格式，支持最完整 |
| `wecomsg` | [WeChatMsg / MemoTrace 留痕](https://github.com/LC044/WeChatMsg) | CSV | 语音/视频/系统通知等无对应类型的消息会被跳过并计数 |
| `telegram` | [Telegram Desktop](https://telegram.org/blog/export-and-more) 官方导出 | Machine-readable JSON（result.json） | 官方功能导出，无合规争议 |
| `plaintext` | 任意工具 / 手动整理 | `.txt` / `.md` / `.log` | 每行一条：`2024-09-11 09:30:00 张三: 内容`；靠行内启发式识别 |
| `docx` | Word 另存 | `.docx` | 段落，或「时间｜发送者｜内容」表格；解析零第三方依赖 |

> 以上链接仅为来源指引，**不构成本项目的使用教程**；导出操作请在各工具官方
> 文档内完成。群聊导出不受支持——只导入双人对话。
>
> **PDF 不支持解析**：「导入体检」会识别出 PDF 并提示你转存为 txt 或 docx。
> 原因是 PDF 的文字是按绝对坐标排版的碎片，无法可靠还原「谁在什么时候说了什么」，
> 硬抽出来只会得到一堆错位文本。

## 多来源合并（v0.3 核心）

真实场景几乎不是「一次导出一份文件」：同一段对话可能在微信那边导过一次、
在 Telegram 那边也导过一次、后来又有人整理成 txt。所以导入被设计成
**可累积、可合并、可单独移除**：

- **一次可上传 1~12 份文件**，来源格式可以混合（微信 CSV + Telegram JSON 一起选）。
- **每份来源各自映射 A/B**：不同应用的账号名不同（微信是 wxid、Telegram 是
  `from_id`、txt 里可能是昵称），所以每份单独选一次「你 / 对方」。这是必须的
  —— 用一套名字去套所有来源必然有一半映射不上。
- **按时间戳自动合并**：全部来源统一归一为 canonical 消息流后，按时间戳全局排序，
  再重算会话切分。两份记录在时间上接续的部分会自然连成一条连续时间轴。
- **跨源重复自动去重**：重叠时间段里的同一句话会被识别为重复并只保留一条
  （去重键 = 时间 + 发送者 + 内容）。门禁 `G8_跨源重复` 会报出去掉了几条。
- **来源会留档**，并且**库永远是「全部已登记来源」重建出来的结果**。这意味着：
  这周先导微信，下周再导 Telegram，第二次导入**不会**丢掉第一次的数据。

### 留档位置与含义

每个好友的数据目录下（`data/` 已在 `.gitignore`，不会进仓库）：

```
data/profiles/<id>/sources/<源文件哈希前16位>.<ext>   源文件存档（按内容哈希去重）
data/profiles/<id>/sources.json                      来源登记表（文件名/格式/映射/条数）
```

界面上「导入记录 → 已导入的来源」可以查看每一份来源，也可以**单独移除**：
移除会删掉它的存档，并按剩余来源立刻重建一次库。

> 你不想要留档也可以：命令行加 `--no-archive`（一次性导入，不做登记，
> 之后无法单独移除这份来源）。

### A/B 选反了会怎样

如果某份来源的「你 / 对方」选反了，跨源去重会**静默失效**（发送者不同 →
去重键不同 → 同一句话被当成两条）。所以系统会自查并显式告警：

> ⚠ 有 N 组消息「时间 + 内容」相同但发送者相反 —— 很可能某份来源的 A/B 选反了

在网页向导的合并预览里、以及命令行输出里都会出现这句话。看到它就去核对下拉框。

> **注意这道自查抓不到的情况**：如果**多份来源一致选反**（比如两份都用了默认值、而默认值
> 恰好都把 A 猜成了对方），彼此之间仍然是对齐的，冲突数为 0 —— 但说话人整体颠倒了。
> 所以默认值不能当答案：
>
> - 向导里每份来源下方会并排显示当前选定的 **A / B 各自的脱敏样例**，请对着它确认
>   「A 那一侧确实是我说话的样子」；
> - 默认映射优先取 `config.yaml` 里 `people.A/B.match` 登记过的账号名，没登记时才退回
>   「消息较多的一方 = A」这种统计猜测，界面上会标明默认值来源；
> - 提交成功后本次的账号名会记回 `config.yaml`，下次导入直接预选。

**已经导错了怎么办**：不用重新上传 —— 来源有存档。「导入记录 → 已导入的来源」里，
每份来源旁边有「**对调 A/B**」，点一下就会按全部来源重建一次库（人格档案与媒体库保留，
分析产物失效需重新分析）。

## 逐格式说明

### chatlab JSONL（WeFlow 导出，原生格式）

每行一个 JSON 对象：

```json
{"_type":"message","platformMessageId":"xxx","timestamp":1751788200,
 "type":0,"content":"今天好累啊","accountName":"你的昵称"}
```

| 字段 | 说明 |
|---|---|
| `_type` | 必须为 `"message"`（其他行会被跳过） |
| `timestamp` | 秒级 Unix 时间戳（也接受毫秒/ISO8601/别名 `ts`/`time`） |
| `type` | `0` 文本 / `7` 图片或表情 / `4` 文件 / `23` 通话 / `24` 小程序 / `25` 引用文本 / `27` 名片 / `80` 撤回 / `99` 转账 |
| `content` | 内容（表情包为文件名，转账为带金额的文本；别名 `text`/`message`） |
| `accountName` | 发送者账号名（别名 `sender`/`talker`/`nick`） |

### WeChatMsg（MemoTrace）CSV

选「聊天记录 → CSV」导出（`id,MsgSvrID,type_name,is_sender,talker,room_name,msg,src,CreateTime`
列布局，旧版 `content` 合并列也兼容）。文本/图片/表情/文件/通话/引用/名片/转账/撤回会入库；
语音、视频、系统通知等 canonical 无对应类型的消息**跳过并计数**；群聊行跳过。
账号名通常是 wxid。

### Telegram Desktop 官方导出 JSON

Telegram Desktop → Settings → Advanced → Export chat history →
Machine-readable JSON（`result.json`）。文本、图片、贴纸、文件会入库；
语音、编辑事件、service 行跳过并计数；超过两个发送者的行按群聊判定跳过。

### txt / md / log（`plaintext`）

这是「非结构化」格式，时间与发送者只能靠行内启发式识别，因此遵守三条纪律：

1. **只认有年份的绝对时间**（`2024-09-11 09:30:00`、`2024/9/11 9:30`、`2024年9月11日 9:30`）。
   「昨天」「上午十点」这类相对时间**一律不猜**，不导入。
2. **没有时间戳的行看作「上一条消息的续行」并入**（聊天导出普遍会软换行）；
   不在任何消息之后的无时间戳行则跳过并计数。体检报告会如实给出
   `续行并入 N 行 / 跳过 M 行`。
3. **无法对应类型的媒体行跳过并计数**（`[语音]`、`[视频]` 等）；
   `[图片]`/`[表情包]`/`[文件]`/`[转账]` 会映射到对应类型。

支持的发送者写法（在时间戳之后）：

| 写法 | 例子 |
|---|---|
| 冒号 | `2024-09-11 09:30:00 张三: 内容`（半/全角冒号都行） |
| Markdown 粗体 | `**张三**: 内容` |
| 中括号 | `2024-09-11 09:30:00【张三】内容` |
| 制表符（表格导出） | `2024-09-11 09:30:00⇥张三⇥内容` |
| 发送者在前 | `张三 2024-09-11 09:30:00 内容` |

编码按 BOM → UTF-8 → GB18030 顺序探测，中文聊天记录常见的 GBK 系能直接读。

> 因为靠启发式，**导入预览里的样例必须逐条核对**。解析不出来不是 bug 就是排版不符；
> 体检会明确告诉你是「认不出格式」还是「认出来了但解析不出消息」。

### Word .docx（`docx`）

- 段落（`w:p`）→ 一行；表格（`w:tbl`）→ 每个单元格用 TAB 拼接成一行。
- 段落内的制表符/换行按原样保留，图片（`w:drawing`/`w:pict`）只计数、不导入
  （图片请走媒体通道）。
- 解析用标准库 `zipfile` + `xml.etree`，**不引入 python-docx**。
- 旧版二进制 `.doc` 不支持，请另存为 `.docx`。

## 导入体检（doctor，只读不写库）

不确定文件能不能导？先体检：

```bash
python run.py doctor --source 你的记录.csv
python run.py doctor --source 整理好的记录.txt
```

输出：格式识别结果、有效消息数、时间跨度、双方候选账号及占比、消息类型分布、
脱敏规则预估命中数、纯文本格式的行解析统计，以及「可导入 / 缺什么 / 建议参数」的结论。
对无法识别的文件给出原因列表，不会崩溃。

## 导入步骤

### 网页向导（推荐，支持多份一起导）

```bash
python run.py server     # 打开 http://127.0.0.1:8015
```

左侧栏「**导入记录**」：

1. **上传**：拖拽或选择文件，**可多选**（`.jsonl / .json / .csv / .txt / .md / .log / .docx`，单份 ≤50MB，单批 ≤12 份）；
2. **逐份确认 + 合并预览**：每份来源单独选「你 / 对方」，下方实时显示
   *合并后条数 / 去重条数 / 合并时间轴 / 来源重叠区*，以及 A/B 选反的告警；
   认不出来的那份点「移除本份」，其余照常导入；
3. **导入结果**：门禁摘要（时间序/双人占比/脱敏残留/未知发送者/跨源重复）。

上传的临时文件在本机 `data/tmp_import/` 处理，链路结束（含失败）立即删除；
**源存档**则落在 `data/profiles/<id>/sources/` 并登记进 `sources.json`，
可在同一界面查看与移除。全程不出本机。详见 [../PRIVACY.md](../PRIVACY.md)。

> 上传后中途关掉向导也不用担心：关闭、「← 重新上传」、以及下次打开向导都会
> `POST /api/import/cancel` 释放在服务端占着的批次（连同临时文件一起删掉），
> 不会出现「明明没在导入却传不上去」。
>
> 就算请求是被强制中断的（刷新页面、预览面板重载），下一次上传也会**直接接管回收**
> 那个悬着的批次（响应里带 `reclaimed: true`），不需要你手动做什么。
> 单个文件认不出来时锁会保留 —— 那是让你在第二步点「移除本份」再继续的可操作状态；
> 预览本身出错则会自动放锁，避免你被一个自己解除不了的锁挡在门外。

### 命令行

```bash
# 单份（老用法不变）
python scripts/import_chat.py --source data/raw/chat.jsonl \
    --sender-a "你的账号名" --sender-b "对方账号名"

# 多份一起导（不同应用各自导出）—— --sender-a/--sender-b 可重复给出
python scripts/import_chat.py \
    --source wechat.csv --sender-a wxid_me --sender-b wxid_ta \
    --source tg.json    --sender-a user_me --sender-b user_ta

# 追加一份新来源（自动与之前导入过的全部来源重建合并）
python scripts/import_chat.py --source 整理.txt --sender-a 张三 --sender-b 李四
```

`--format` 可选 `auto`（默认）/ `chatlab` / `wecomsg` / `telegram` / `plaintext` / `docx`。

两个开关：
- `--no-reset`：不重建，把给定来源追加写入现有库（旧行为，不做来源登记）；
- `--no-archive`：不登记来源（一次性导入，之后无法单独移除）。

也可以把账号名映射写进 `config.yaml`（支持列表，可写多个来源的账号名）：

```yaml
people:
  A: { key: "A", display: "你", match: ["wxid_me", "user_me", "张三"] }
  B: { key: "B", display: "TA", match: ["wxid_ta", "user_ta", "李四"] }
```

> 约定：A 是**你本人**（对话里的「你」，推演中由你亲自输入），B 是对方
> （数字人格一侧）。账号名必须与导出文件里的发送者字段逐字一致。

## 媒体导入（表情包 / 图片）

媒体与聊天记录是**两条独立通道**：聊天记录里只有文件名，真正的图片文件往往在另一次
导出里、甚至散落在你自己收集的文件夹里。所以媒体单独导入，导入后按**文件名精确匹配**
与消息自动关联（匹配不上就留空，绝不猜测归类）。

### 怎么导

网页左侧「导入记录 → 打开媒体库」：

- **拖拽 / 选择图片**（`.gif / .png / .jpg / .jpeg / .webp / .bmp`，单张 ≤20MB）；
- 或填**本机目录路径**一次性导入整个文件夹（典型用法：WeFlow 导出的 `Emojis` 文件夹）；
- 类型可指定「表情包 / 图片」，或留「自动」（`gif`/`webp` 算表情包，其余算图片）。

### 存哪、怎么去重

```
data/profiles/<id>/media/<内容哈希前16位><ext>    文件存档（同内容只存一份）
media 表                                          索引（哈希/文件名/类型/尺寸）
message_media 表                                  与消息的关联
```

- 按内容哈希去重：同一张图重复导入只会记一条。
- 媒体索引**独立于聊天记录**：重新导入聊天记录、切换来源都不会动媒体库。
- 消息 ↔ 媒体关联表会在每次导入后重算；删除媒体只影响显示，不动聊天记录。

### ⚠️ 红线：媒体不做脱敏、不进 LLM

聊天文字会被脱敏（手机号 → `[手机号]`），但**图片是原始二进制，不会有任何处理**。
一张身份证截图、一张快递单照片、一张含地址的聊天截图，导入后就原样躺在
`data/profiles/<id>/media/` 里。

因此：

- 媒体**不参与任何分析与 LLM 调用**，只用于在对话界面里显示对方真实用过的表情/图片；
- 导入前请自己确认图片不含你不希望留在本机的敏感信息；
- 媒体库与聊天记录一起随好友数据目录走，删除好友时会一并删除。

## 导入后会发生什么

1. **去噪**：统一空白/换行；
2. **脱敏**：命中隐私模式的内容替换为占位符，并统计 `has_privacy`；
3. **会话化**：相邻消息间隔 > 30 分钟视为两个会话（可配置）；
4. **入库**：写入 `data/ifwe_v1.db` 的 `messages / sessions / daily_stats`，
   以及来源台账 `import_sources`；
5. **质量门禁**：

| 门禁 | 检查 | 是否阻塞 |
|---|---|---|
| `G2_时间序列有序` | 合并排序后 ts 必须非降 | 阻塞 |
| `G3_双人占比` | A / B 各占 > 25%（映射错误会在这里暴露） | 阻塞 |
| `G4_长断档告警` | > 30 天的断档样本 | 告警 |
| `G5_脱敏残留` | 全量 `content_clean` 复扫隐私模式 | 阻塞 |
| `G7_未知发送者/类型` | 未映射到 A/B 的发送者、未知消息类型 | 阻塞 |
| `G8_跨源重复` | 去重条数、按来源分布、映射冲突数 | 告警 |

任一阻塞项失败以非零退出码提示；产出报告 `data/phase1_验收报告.md` 与
`data/phase1_summary.json`（含每份来源的条数与映射）。

## 数据规范 v2（相对 v1 的变更）

| 变更 | 内容 |
|---|---|
| `messages` 增列 | `source_id`（来源登记 id）、`dedup_key`（跨源去重键） |
| 新表 | `import_sources`（来源台账）、`media`（媒体索引）、`message_media`（消息↔媒体关联） |
| `meta.spec_version` | `"1"` → `"2"` |
| 主键语义修正 | 无平台消息 id 时，兜底 id 由「时间戳-x」改为「时间戳-来源内序号」——同秒多条消息不再互相覆盖 |

旧库（v1 结构）在首次访问时会被幂等升级（`phase1_ingest.ensure_v2_schema()` 补列 + 建索引），
不需要手动迁移。

## 常见问题

**Q: 门禁提示「双人占比」未通过？**
大概率某份来源的账号名映射错了（A/B 写反或拼写不一致导致一方被记为未知发送者 X）。

**Q: 消息条数比两份导出加起来少？**
那是跨源去重生效了：重叠时间段里的同一句话只保留一条。看 `G8_跨源重复` 的
`removed` 数，或体检预览里的「跨源去重」一行。

**Q: 提示「有 N 组消息时间+内容相同但发送者相反」？**
某份来源的 A/B 选反了。去合并预览里把那份来源的两个下拉框换过来。

**Q: txt / md 导入条数明显偏少？**
该文件的排版不是「一行一条」。看体检里的「行解析」统计：
`续行并入 N 行` 是正常的多行消息；`跳过 M 行` 说明这些行既无时间戳也不在任何消息内。

**Q: 想重新导入？**
默认每次导入都会按「全部已登记来源」重建当前好友的库（`--no-reset` 除外）；
你的源文件只读、永不修改，源存档也不会被动。重建会清空推演线与分析产物，
**人格档案与媒体库保留**。

**Q: 不想要来源留档？**
命令行加 `--no-archive`，或导入后在「已导入的来源」里逐份移除。
